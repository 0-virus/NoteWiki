# 이벤트 기반 아키텍처 (Event-Driven Architecture)

## 한 줄 정의

**서비스들이 서로를 직접 호출하는 대신, "무슨 일이 일어났다"는 이벤트를 발행하고
관심 있는 쪽이 구독해 반응하는 아키텍처.**

## 명령과 이벤트의 차이

같은 상황을 표현하는 두 방식이 있다.

```
명령(Command):  "결제를 처리해라"     → 받는 대상이 정해져 있다. 응답을 기대한다.
이벤트(Event):  "주문이 생성되었다"   → 받는 대상을 모른다. 사실의 기록일 뿐이다.
```

**이 한 끗 차이가 결합도를 결정한다.** 명령을 보내려면 누구에게 보낼지 알아야 하지만,
이벤트는 "일어난 일"을 말할 뿐이므로 발행자가 소비자를 알 필요가 없다.

## 구조의 전환

**호출 기반 (동기·강한 결합)**
```
Order Service → HTTP → Payment Service
              → HTTP → Inventory Service
              → HTTP → Shipping Service
```
서비스 하나가 늘 때마다 Order Service 코드가 바뀐다. 하나가 느려지면 전부 느려진다.

**이벤트 기반 (비동기·느슨한 결합)**
```
Order Service
     ↓ OrderCreated
   Kafka
     ├→ Payment
     ├→ Inventory
     └→ Analytics
```
Order Service는 이벤트만 남긴다. 소비자가 추가돼도 발행 코드는 그대로 —
**Loose Coupling**이 코드 수준에서 실현된다.

## 동기 통신과 비동기 통신

```
REST(동기)              메시징(비동기)
A → "처리해줘"          A → 이벤트 기록 → 끝
B 처리 중... A는 대기    A는 자기 일 계속
B → "완료했어"          B가 나중에 가져가 처리
A 계속 실행
```

동기는 **결과가 즉시 필요할 때**, 비동기는 **결과를 기다릴 필요가 없을 때** 쓴다.
호출자의 응답 시간에 피호출자의 처리 시간이 포함되는지 여부가 갈림길이다.

## 얻는 것과 잃는 것

**얻는 것**
- 결합도 감소 — 소비자 추가·제거가 발행자에 영향을 주지 않는다
- 장애 격리 — 소비자가 죽어도 이벤트는 남는다
- 확장성 — 트래픽 급증을 브로커가 완충한다
- 감사 이력 — 이벤트 로그 자체가 "무슨 일이 있었는가"의 기록이 된다

**잃는 것**
- **즉시 일관성** — 발행 직후 소비자 상태는 아직 옛날이다. [[eventual-consistency|최종 일관성]]을 전제로 설계해야 한다
- **추적 난이도** — 하나의 사용자 요청이 여러 서비스에 흩어진다. 분산 추적·상관관계 ID가 필수가 된다
- **디버깅·테스트 난이도** — "어디서 끊겼는가"를 눈으로 좇기 어렵다
- **중복 처리 대비 의무** — [[message-delivery-semantics|At-least-once]]가 기본이므로 [[idempotency|멱등성]]이 선택이 아니라 필수다

**"결합도를 낮추는 대신 복잡도를 다른 곳으로 옮기는 것"** — 없애는 게 아니라 옮기는 거래다.
서비스가 두세 개뿐이라면 직접 호출이 더 나을 수 있다.

## REST API와 경쟁 관계가 아니다

이벤트 기반을 도입한다고 REST를 버리는 것이 아니다. 보통 **함께** 쓴다.

```
사용자 → HTTP → Order API → DB 저장
                    ↓
                  Kafka → 다른 서비스들
```

- **사용자 ↔ 시스템**: 즉시 응답이 필요하다 → [[restful-api|REST]]
- **시스템 ↔ 시스템**: 결과를 기다릴 필요가 없다 → 이벤트

**동기 경계와 비동기 경계를 어디에 그을 것인가**가 실제 설계 문제다.

## 대표 사례

- **마이크로서비스 간 이벤트 전달** — 가장 흔한 용도
- **로그 수집** — 여러 서버 로그를 한 파이프라인으로
- **데이터 파이프라인** — 운영 DB → 분석 시스템·검색엔진으로 흘려보내기 ([[change-data-capture|CDC]])
- **실시간 분석·추천** — 클릭·검색·구매 이벤트를 실시간 집계

## 영균의 실무 맥락

금융 도메인의 대출 신청 흐름이 좋은 예다. 신청이 접수되면 심사·알림·감사 로그·분석이
모두 그 사실을 알아야 하는데, 신청 서비스가 이들을 직접 호출하면 하나가 느려질 때
사용자의 신청 자체가 느려진다.

```
                 ┌→ 심사
Loan Service → Kafka ├→ 알림
                 ├→ 감사 로그
                 └→ 분석
```

```json
{ "eventType": "LOAN_APPLICATION_CREATED",
  "applicationId": "A10001", "customerId": "C5001" }
```

신청 서비스는 이 시스템들의 세부 구현을 알 필요가 없다. **감사 로그가 자연히 남는다**는
점도 금융에서 특히 값지다 — 이벤트 로그 자체가 "언제 무슨 일이 있었는가"의 증거다.
(위 값들은 구조 설명용 가상 예시다.)
