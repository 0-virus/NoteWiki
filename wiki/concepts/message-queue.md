# 메시지 큐 (Message Queue)

## 한 줄 정의

**시스템과 시스템 사이에 끼워 넣는, 작업 요청(메시지)을 보관하는 대기열.**
보내는 쪽(Producer)과 받는 쪽(Consumer)이 서로를 직접 호출하지 않고 큐를 통해 소통한다.

## 왜 필요한가 — 직접 호출이 만드는 3가지 문제

주문 서버가 이메일 서버를 HTTP로 직접 호출한다고 하자.

```
사용자 주문 → 주문 서버 → 이메일 서버
```

이 단순한 구조에는 세 개의 결함이 숨어 있다.

**① 장애 전파.** 이메일 서버가 느려지거나 죽으면, 그 응답을 기다리는 주문 서버까지
느려진다. 이메일 발송은 주문 성사에 **필수가 아닌데도** 주문 자체를 막는다.
동기 호출은 호출자의 스레드를 붙잡아 두기 때문이다 ([[thread]]·[[thread-pool]]의
관점에서 보면, 응답을 기다리는 스레드는 그동안 아무 일도 못 하는 낭비다).

**② 처리 용량 불일치.** 주문 서버는 초당 10,000건을 처리하는데 이메일 서버는 1,000건이
한계라면, 이벤트 트래픽이 몰리는 순간 느린 쪽이 먼저 터진다.

**③ 강한 결합.** A가 B를 호출하려면 A가 B의 주소·API 스펙을 알아야 한다. 수신 측이
하나 늘 때마다 발신 측 코드를 고쳐야 한다.

큐를 중간에 두면 셋 다 완화된다.

```
주문 서버 → [ Message Queue ] → 이메일 서버
```

주문 서버는 큐에 이런 메시지만 넣고 자기 할 일로 돌아간다.

```json
{ "type": "SEND_ORDER_EMAIL", "orderId": 1001 }
```

## 기본 구조

```
Producer  →  Message Queue  →  Consumer
(보내는 쪽)     (대기열)        (받아 처리하는 쪽)
```

- **Producer** — 메시지를 만들어 넣는 프로그램 (주문 서비스, 배치, 웹 서버…)
- **Queue** — 메시지가 쌓여 대기하는 공간
- **Consumer** — 큐에서 꺼내 실제 작업(메일 발송, DB 저장, 외부 API 호출, PDF 생성)을 수행

## 네 가지 효과 — "왜 이렇게 동작하는가"

### 1. 비동기 처리
Producer는 "큐에 넣었다"까지만 확인하고 끝낸다. Consumer의 처리 완료를 기다리지 않는다.
**응답 시간에서 후속 작업을 떼어내는 것**이 핵심이다.

### 2. 느슨한 결합 (Loose Coupling)
Producer는 Consumer가 누구인지, 몇 개인지, 살아 있는지 모른다. 아는 것은 큐(또는 토픽)
이름뿐이다. 수신자를 추가해도 발신 코드는 그대로다.

### 3. 트래픽 완충 (Buffer)
```
주문 10,000건/s
      ↓
    Queue      ← 9,000건이 여기 대기
      ↓
이메일 서버 (1,000건/s로 자기 속도대로 소비)
```
큐가 **속도 차이를 흡수하는 완충재**가 된다. 이 구조 덕분에 느린 Consumer를 보호하면서도
빠른 Producer를 늦추지 않는다. ([[java-buffer]]의 버퍼가 "속도 차 나는 두 장치 사이의
임시 저장소"인 것과 정확히 같은 원리 — 계층만 다르다.)

### 4. 장애 내성
Consumer가 10분간 죽어도 메시지는 큐에 남는다. 복구되면 밀린 것부터 처리한다.
직접 호출이었다면 그 10분간의 요청은 전부 유실됐을 것이다.

## 대가 — 공짜가 아니다

### 중복 처리 가능성
Consumer가 작업을 끝낸 **직후, 완료 보고를 보내기 전에** 죽으면 큐는 "아직 처리 안 됐다"고
판단해 메시지를 다시 전달한다.

```
Message A → 처리 성공 → (ACK 전송 직전 다운) → 재전달 → 또 처리
```

**메시지 큐가 중복을 완전히 막을 수 없는 이유**는 "작업 수행"과 "완료 보고"가 원자적이지
않기 때문이다. 그래서 Consumer 쪽 [[idempotency|멱등성]]이 사실상 필수 방어선이 된다.

### ACK — 완료 확인
Consumer가 처리를 마쳤음을 큐에 알리는 신호가 **ACK**다. 큐는 ACK를 받아야 메시지를
제거하고, 못 받으면 재전달한다. 자세한 보장 수준은
[[message-delivery-semantics|메시지 전달 보장]] 참고.

### 영원히 실패하는 메시지
잘못된 데이터처럼 몇 번을 재시도해도 실패하는 메시지가 무한 재시도를 돌면 시스템 전체가
망가진다. 그래서 일정 횟수 실패한 메시지는 [[dead-letter-queue|DLQ]]로 격리한다.

### 그 외
- 추적이 어려워진다 — 요청 흐름이 여러 시스템에 흩어진다
- 브로커 자체가 운영·모니터링 대상이 하나 더 늘어난다
- 즉시 일관성을 포기하고 [[eventual-consistency|최종 일관성]]을 받아들여야 한다

## 전체 프로세스

```
Producer
   │
   ▼
┌──────── Queue ────────┐
│ Message1              │
│ Message2              │
│ Message3              │
└───────────────────────┘
   │
   ▼
Consumer
   ├─ 성공 → ACK → 큐에서 제거
   └─ 실패 → Retry → 반복 실패 → DLQ
```

## 여러 Consumer로 나눠 처리하기

큐에 메시지가 1,000개 쌓였는데 Consumer가 하나면 느리다. Consumer를 늘리면 큐가
메시지를 나눠 준다.

```
Queue ├→ Consumer A
      ├→ Consumer B
      └→ Consumer C
```

이를 **Competing Consumers 패턴**이라 한다. 같은 큐 안에서는 **한 메시지를 한 Consumer만**
처리하는 것이 기본 목적이다 — 그래야 작업이 중복되지 않는다.
([[thread-pool]]이 작업 큐 하나를 여러 워커 스레드가 나눠 처리하는 것과 같은 구조가,
프로세스·서버 단위로 확장된 형태다.)

## 구현체

메시지 큐는 개념이고, 이를 실제로 제공하는 서버를 **메시지 브로커(Message Broker)**라 한다.

- [[rabbitmq]] — 전통적 메시지 브로커. 작업 분배·복잡한 라우팅에 강함
- [[kafka]] — 분산 이벤트 스트리밍 플랫폼. 저장·재처리·대용량에 강함
- 그 외: ActiveMQ, Amazon SQS, Redis Pub/Sub(전달만 하고 저장하지 않음 — 구독자가 없으면 유실)

둘의 선택 기준은 [[rabbitmq-vs-kafka]] 참고.

## 영균의 실무 맥락

[[outbox-pattern]]을 공부하며 "그래서 메시지를 어디로 보내는데?"라는 질문에서 이어진
개념. 곧 실무 프로젝트에서 [[kafka]]를 다루게 되어 원리부터 정리했다.
**직접 호출(REST) → 메시지 큐 → 이벤트 스트리밍**으로 이어지는 통신 방식의 스펙트럼에서
첫 번째 갈림길에 해당한다.
