# 데이터베이스 마이그레이션 (Database Migration / 형상 관리)

## 한 줄 정의

**DB 스키마의 변경 이력을 코드처럼 버전 관리하고, 어떤 환경의 DB든 같은 순서로 같은 상태에 도달하게 만드는 것.**

> 소스 코드의 이력을 Git으로 관리하듯, DB 이력을 마이그레이션 툴로 관리한다.

## 왜 필요한가 — 문제의 뿌리

코드는 Git이 있어서 "누가 언제 무엇을 왜 바꿨는지"가 남고, `git clone` 한 번으로 모든 개발자가 같은 상태가 된다.
**DB에는 그게 없다.** DB는 파일이 아니라 *살아 있는 상태*라서, 그냥 두면 이런 일이 벌어진다.

```
로컬 DB (내 노트북)   : member 테이블에 phone 컬럼 있음
로컬 DB (팀원 노트북) : phone 없음, 대신 tel 있음
테스트 DB            : 2주 전 스키마
운영 DB              : 아무도 정확히 모름 ← 가장 무서운 상태
```

환경이 여러 개(로컬/테스트/운영)면 **스키마가 갈라지고**, 갈라진 걸 맞추는 순간이 곧 장애다.

### 개발 단계에서는 왜 이 문제가 안 보이나

[[jpa]]를 쓰면 엔티티 클래스가 곧 스키마다. 엔티티에 필드를 하나 추가하면
[[hibernate]]의 [[hibernate-ddl-auto|ddl-auto]] 설정이 알아서 테이블을 다시 만들어 준다.
그래서 **로컬에서는 마이그레이션의 필요성을 못 느낀다.**

문제는 운영이다. 운영 DB는 지울 수 없다 — 안에 진짜 데이터가 있다.
그래서 운영에서는 반드시 이런 DDL을 직접 써야 한다.

```sql
ALTER TABLE student ADD COLUMN number VARCHAR(20) NOT NULL;
```

이 방식의 두 가지 결함:

1. **실수하기 쉽다** — 사람이 콘솔에 직접 친다. 오타 하나, 빠뜨린 환경 하나가 곧 장애.
2. **이력이 안 남는다** — 나중에 "이 컬럼 언제 왜 생겼지?"에 아무도 답하지 못한다.

게다가 `ALTER TABLE`은 그 자체로 위험하다 → [[ddl-lock]] (메타데이터 락으로 서비스가 멈추는 구조).

## 형상 관리의 이점

| 이점 | 원리 |
| --- | --- |
| **변경 이력이 남는다** | 마이그레이션 스크립트 자체가 Git에 커밋되는 파일이다. 장애 시 "언제 뭐가 바뀌었나"를 코드 히스토리로 추적 |
| **작업이 안전해진다** | 사람이 콘솔에 치는 대신 **코드가 실행**한다. 리뷰 가능하고, 재현 가능하고, 자동화 가능 |
| **환경이 수렴한다** | 어느 환경이든 "버전 N까지 적용" 상태로 정의된다. 스키마 드리프트가 사라짐 |
| **배포에 얹을 수 있다** | 앱이 뜰 때 자동으로 미적용 스크립트를 실행 → CD 파이프라인의 일부가 됨 |

## 핵심 원리 — "현재 버전"을 DB 자신이 기록한다

마이그레이션 툴의 발상은 단순하다.

```
DB 안에 "지금까지 적용한 스크립트 목록" 테이블을 하나 둔다.
  ↓
앱 시작 시 스크립트 폴더를 스캔한다.
  ↓
그 테이블에 없는 스크립트만, 버전 순서대로 실행한다.
  ↓
실행 결과를 그 테이블에 기록한다.
```

**상태를 DB 자신이 들고 있다**는 것이 핵심이다. 그래서 로컬이든 운영이든 같은 코드를 실행해도
각자 자기에게 필요한 만큼만 따라잡는다(멱등성). [[flyway]]에서는 이 테이블이
`flyway_schema_history`다.

## 대표 도구

| 도구 | 스크립트 형식 | 특징 |
| --- | --- | --- |
| **[[flyway]]** | SQL 중심 (Java도 가능) | 단순·직관적. 파일명 규칙으로 버전 관리 |
| Liquibase | XML/YAML/JSON/SQL | DB 벤더 중립 추상화, 롤백 무료. 대신 학습 곡선이 큼 |

> TODO: Liquibase는 아직 독립 페이지 없음 — 실제로 비교 검토할 때 만든다.

## 영균의 맥락

개인 Spring 프로젝트(ZeroVerse 등)에 적용하려는 기술.
지금은 `ddl-auto: update`로 굴러가지만, **배포하는 순간 이 방식은 못 쓴다.**
"프로젝트로 완전한 웹 서비스 배포"가 목표라면 마이그레이션은 선택이 아니라 통과해야 하는 관문이다.
전체 그림은 [[entity-to-production-schema]] 참조.
