# Dead Letter Queue (DLQ)

## 한 줄 정의

**정상적으로 처리할 수 없는 메시지를 본래 큐에서 떼어내 따로 보관하는 별도의 큐.**
"죽은 편지 보관함" — 배달 실패한 우편물을 반송함에 모아 두는 것과 같다.

## 왜 필요한가 — 재시도만으로는 안 되는 이유

[[message-queue|메시지 큐]]는 실패한 메시지를 재시도한다. 외부 API의 일시 장애처럼
**시간이 지나면 성공할 오류**에는 이게 정답이다.

문제는 **절대 성공할 수 없는 메시지**다. 필수 필드가 빠졌거나, 참조하는 데이터가 삭제됐거나,
JSON 자체가 깨진 메시지는 백 번을 재시도해도 실패한다. 이 메시지를 계속 재시도하면:

```
Main Queue
  [독성 메시지] ← 큐 맨 앞에서 실패 → 재삽입 → 또 실패 → 무한 반복
  [정상 메시지] ← 뒤에서 계속 대기, 영원히 처리 안 됨
```

- Consumer 자원을 실패에만 소모한다
- 뒤의 정상 메시지 처리가 밀린다 (**head-of-line blocking**)
- 로그가 같은 에러로 도배돼 진짜 문제를 못 본다

이렇게 큐 전체를 마비시키는 메시지를 **poison message(독성 메시지)**라 한다.

## 해법 — 격리

일정 횟수(보통 3~5회) 실패하면 메시지를 본 큐에서 빼내 DLQ로 옮긴다.

```
Main Queue → Consumer → 실패
                         ↓
                      Retry ×N
                         ↓
                    여전히 실패
                         ↓
                       DLQ  (운영자가 나중에 확인)
```

핵심은 **버리지 않고 격리한다**는 점이다. 메시지를 삭제하면 데이터가 유실되고, 남겨두면
큐가 막힌다. DLQ는 그 사이의 절충 — **파이프라인은 흐르게 하면서 증거는 보존한다.**

관례상 이름은 원래 큐 뒤에 접미사를 붙인다.

```
email.queue  →  email.dlq
```

## 재시도 정책 — 백오프

DLQ로 보내기 전 재시도도 아무렇게나 하면 안 된다. 실패 즉시 바로 재시도하면 이미 힘든
상대 시스템을 더 몰아붙여 장애를 키운다(retry storm). 그래서 **지연 재시도**를 둔다.

```
1초 후 → 10초 후 → 1분 후 → DLQ
```

간격을 점점 늘리는 것이 **지수 백오프**, 여기에 임의 지연을 더해 여러 Consumer가 동시에
재시도하지 않게 하는 것이 **지터**다. ([[outbox-pattern]]의 Publisher 재시도 정책과
같은 원리 — 위치만 다르다.)

또한 **일시적 오류와 영구적 오류를 구분**하는 것이 중요하다. 영구적 오류(스키마 위반,
인증 실패)는 재시도할 이유가 없으니 곧장 DLQ로 보내는 편이 낫다.

## 운영 — DLQ에 쌓인 다음은?

DLQ는 만들어 두는 것으로 끝이 아니다.

1. **모니터링** — DLQ에 메시지가 들어오면 알림. DLQ 적재량은 시스템 건강 지표다
2. **원인 분석** — 메시지 본문 + 실패 이유(브로커가 헤더에 남겨준다) 확인
3. **재처리(replay)** — 버그 수정 후 DLQ 메시지를 본 큐로 되돌려 다시 흘린다
4. **폐기** — 재처리 의미가 없으면 기록 남기고 삭제

**DLQ가 계속 비어 있다면 정상이 아니라 "DLQ 설정이 잘못됐을 가능성"도 의심**해야 한다.

## 브로커별 구현 차이

| | [[rabbitmq]] | [[kafka]] |
|---|---|---|
| 지원 방식 | 큐 속성으로 내장 (`x-dead-letter-exchange`) | 브로커 기본 기능 아님 |
| 진입 조건 | NACK(재큐 안 함)·TTL 만료·큐 길이 초과 | 애플리케이션/프레임워크가 직접 별도 토픽으로 발행 |
| 체감 | 자연스럽다 | 별도 설계가 필요하다 |

Kafka에 DLQ가 내장돼 있지 않은 이유는 구조에서 나온다. Kafka는 메시지를 소비해도 지우지
않고 [[kafka-topic-partition|오프셋]]만 전진시키므로, "실패한 하나를 큐에서 빼낸다"는
동작 자체가 존재하지 않는다. 그래서 Kafka에서는 실패한 레코드를 애플리케이션이 직접
`orders.DLT` 같은 별도 토픽으로 다시 produce 한다 (Spring Kafka의 `DeadLetterPublishingRecoverer`).
