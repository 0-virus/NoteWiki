# 네트워크 타임아웃 — 어느 단계에서 기다렸는가

같은 “요청 실패”라도 기다린 단계가 다르면 원인과 대응이 다르다. 타임아웃은 실패 원인의 확정 판정이 아니라 **정해진 시간 안에 해당 단계가 완료되지 않았다는 관찰**이다.

| 증상·제한 시간 | 의미 | 우선 확인할 것 |
| --- | --- | --- |
| Connect timeout | 연결 수립이 시간 안에 완료되지 않음 | 주소·포트·라우팅·방화벽·상대 가용성 |
| Read timeout | 읽기 대기가 설정된 시간을 초과 | 상대 처리 지연·네트워크·미완성 전문·길이 해석 |
| Write timeout | 쓰기가 제한 시간 안에 진행·완료되지 않음 | 송신 버퍼·상대 읽기·네트워크 정체 |
| 풀 획득 timeout | 기존 연결을 빌리는 데 실패 | 풀 고갈·반납 누락·장시간 점유 |
| Connection refused | 연결 시도에 명시적인 거부를 받음 | 리스닝 포트·바인딩 주소·적극적 방화벽 거부 |
| Connection reset | 연결이 RST 등으로 중단됨 | 상대 종료·중간 장비·연결 수명 |

DNS·TLS 핸드셰이크·전체 요청 제한 시간을 별도로 두는 라이브러리도 있다. 설정 이름만 보고 범위를 단정하지 말고 해당 클라이언트의 계약을 확인한다. 특히 [[hikaricp]]의 `connectionTimeout`은 풀에서 연결을 빌리는 대기 시간이다 → [[connection-pool]].

## 읽기 타임아웃이 전문 오류일 수 있는 이유

상대가 500바이트를 보냈는데 길이 해석 오류로 700바이트를 기다리면, 네트워크가 정상이어도 끝나지 않는다. [[tcp-message-framing]]의 길이 단위·헤더 포함 여부·누적 바이트 수를 함께 확인해야 한다.

읽기별 대기 시간을 제한해도 데이터가 조금씩 계속 도착하면 전체 전문 수신이 오래 걸릴 수 있다. 전체 처리 마감과 개별 읽기 제한은 다른 기준이다.

## 응답을 못 받았다고 업무가 실패한 것은 아니다

```text
요청 전송 → 상대 DB 반영 → 응답 중 연결 단절
```

송신자는 timeout을 보지만 상대 업무는 이미 끝났을 수 있다. 따라서 [[tcp]] ACK·HTTP 상태·업무 응답을 구분하고, 재시도에는 [[idempotency]]를 고려한다. TCP의 바이트 재전송과 애플리케이션의 업무 요청 재시도도 서로 다르다.

두 연결을 잇는 시스템은 [[tcp-to-http-gateway-flow]]에서 외부 수신, 내부 호출, 외부 응답을 나눠 관찰한다. 출처: [[tcp-ip-dialogue]].
