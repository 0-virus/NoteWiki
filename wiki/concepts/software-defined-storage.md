# 소프트웨어 정의 스토리지 (SDS)

SDS는 저장 서비스와 관리 정책을 하드웨어와 분리해 소프트웨어에서 제어하는 방식이다. 스토리지 가상화가 장치를 논리 자원으로 보여주는 데 초점을 둔다면, SDS는 그 자원의 배치·보호·복구 정책까지 다룬다. [[hyperconverged-infrastructure|HCI]]에서는 보통 여러 노드의 로컬 디스크를 하나의 논리 풀로 제공한다. 전용 스토리지 서버에도 SDS를 구축할 수 있다. [Red Hat의 SDS 개요](https://www.redhat.com/en/topics/data-storage/software-defined-storage)

## 용량과 장애 허용 범위

| 노드당 데이터용 SSD 2TB × 3 | 이론상 사용자 데이터 용량 |
| --- | --- |
| 원시 용량 합계 | 6TB |
| 전체 사본 2개 유지 | 약 3TB |
| 전체 사본 3개 유지 | 약 2TB |

위 복제 계산은 전체 사본 수로 원시 용량을 나눈 값이다. 실제 예산에는 메타데이터·시스템 사용량·장애 후 재구축 공간이 들어간다. 이레이저 코딩은 원본을 여러 조각과 복구용 조각으로 나누므로 별도의 용량·처리 비용 계산이 필요하다. 사본을 노드나 랙 단위로 분산하면 같은 장애로 여러 사본을 함께 잃을 가능성을 줄일 수 있다. 장애 후 쓰기 가능 여부는 남은 사본 수 외에도 배치 정책과 쓰기 허용 조건에 좌우된다. [Ceph 풀과 배치 정책](https://docs.ceph.com/en/latest/rados/operations/pools/)

## 데이터 보호의 목적

| 방식 | 쓰는 이유 |
| --- | --- |
| 복제 | 디스크나 노드가 고장 났을 때 다른 사본으로 접근한다. 삭제나 잘못된 변경도 복제될 수 있다. |
| 스냅샷 | 특정 시점으로 되돌린다. 원본과 저장소를 공유하면 저장소 장애의 영향도 함께 받는다. |
| 백업 | 격리해 보존한 사본으로 복구한다. 보존 기간과 실제 복구 가능 여부가 중요하다. |
| 재해 복구 (DR) | 사이트 단위 장애 이후에도 다른 위치에서 데이터와 실행 환경을 복구한다. |
