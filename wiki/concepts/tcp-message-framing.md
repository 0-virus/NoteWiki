# TCP 메시지 프레이밍 — 전문 한 건의 경계를 찾기

[[tcp]]에는 전문 한 건이라는 단위가 없다. **프레이밍은 바이트 스트림에서 애플리케이션 메시지의 시작과 끝을 판단하는 규칙**이다.

```text
송신: [전문 A][전문 B]
읽기 1: [A 앞부분]
읽기 2: [A 나머지][B 앞부분]
읽기 3: [B 나머지]
```

이것은 정상적인 수신이다. 버퍼에 들어온 데이터를 누적해 완성된 전문만 꺼내고 다음 전문의 일부는 남겨야 한다. 단순히 버퍼를 크게 잡는 것으로 해결되지 않는다.

## 경계를 정의하는 방법

| 방식 | 끝을 판단하는 기준 | 주의점 |
| --- | --- | --- |
| 전체 고정 길이 | 항상 N바이트 | 송수신자가 같은 길이·인코딩에 합의 |
| 길이 헤더 | 헤더가 지정한 N바이트 | 헤더 포함 길이인지 본문 길이인지 구분 |
| 구분자 | 줄바꿈 등 약속한 구분자 | 본문 안 같은 값의 이스케이프 규칙 필요 |

고정 길이 **필드**를 쓰는 전문이라도 거래 종류에 따라 전체 길이가 달라질 수 있다. 필드 형식과 전체 메시지 경계는 따로 확인한다. JSON이라는 형식만 정했다고 연속 JSON 문서의 경계까지 자동으로 결정되지는 않는다.

## 길이 헤더 방식의 수신 절차

1. 길이 필드를 해석할 수 있을 만큼 헤더를 누적한다.
2. 길이 단위·바이트 순서·헤더 포함 여부를 규격에 맞게 해석한다.
3. 최소·최대 길이를 확인한 뒤 필요한 나머지 바이트를 기다린다.
4. 한 전문의 바이트 범위를 확정하고 필드를 파싱한다.
5. 남은 바이트는 다음 전문을 위해 보관한다. 대기 중 EOF나 제한 시간 초과는 미완성 전문으로 처리한다.

Java `InputStream.read(byte[], off, len)`은 요청한 길이보다 적게 읽을 수 있다. `readNBytes`도 EOF에 도달하면 요청량보다 적게 반환할 수 있으므로 반환 길이를 확인해야 한다. [Java InputStream 문서](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/io/InputStream.html)

## 구현에서 나누어 볼 경계

- **바이트와 문자**: 길이가 바이트 기준이면 문자열 길이로 자르지 않는다. 멀티바이트 문자는 여러 번의 읽기에 걸칠 수 있어 디코딩 시 경계를 보존해야 한다.
- **프레이밍과 파싱**: 전문 전체를 확보하는 일과 각 필드의 뜻을 읽는 일은 별개다.
- **읽기 대기와 전체 제한 시간**: 조금씩 계속 도착하면 읽기별 타임아웃만으로 전체 처리 시간을 제한하지 못할 수 있다 → [[network-timeout]].
- **부분 쓰기**: 저수준·비차단 API에서는 실제 쓴 바이트 수를 확인한다. 구체적인 처리는 사용하는 API 계약을 따른다.

[[java-buffer]]가 입력을 모아두는 원리라면, 프레이밍은 그 버퍼에서 **어디까지 한 건으로 꺼낼지** 정하는 규칙이다. 연동 적용은 [[tcp-to-http-gateway-flow]], 담당 시스템은 [[protocol-gateway]] 참고.
