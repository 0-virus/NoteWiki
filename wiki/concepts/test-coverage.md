# 테스트 커버리지 (Test Coverage)

## 한 줄 정의

**테스트를 실행했을 때 소스 코드 중 실제로 실행된 부분의 비율.**

## 커버리지가 측정하는 것 / 못 하는 것 (★ 먼저 알아야 할 것)

> **100%라고 해서 버그가 없다는 뜻이 아니다.**
> 코드가 **실행은 됐지만 결과를 검증(assert)하지 않았을 수도** 있기 때문이다.

커버리지 도구는 "이 줄에 실행 흔적이 찍혔는가"만 센다. 그 줄의 결과가 맞는지는 모른다.
극단적으로, 모든 메서드를 호출하기만 하고 `assert`를 하나도 안 써도 커버리지는 100%가 나온다.

그럼 왜 보나? **비대칭성** 때문이다.

- 커버리지가 높다 → 좋은 테스트라는 **보장은 안 된다**
- 커버리지가 낮다 → 그 코드는 테스트가 **지나가 본 적조차 없다**는 뜻이다 (확정적 나쁨)

즉 커버리지는 품질 지표가 아니라 **최소한의 안전망(하한선)** 이다. "이만큼은 최소한 실행은 해봤다"를 보장한다.

## 4가지 측정 단위

| 지표 | 세는 것 |
| --- | --- |
| **Line Coverage** | 소스 코드 **줄** 중 한 번이라도 실행된 줄의 비율 |
| **Branch Coverage** | **조건 분기**(`if`·`while`·`&&`·`||`·`when`/`switch`) 중 실제로 거쳐간 분기의 비율 |
| Function Coverage | **함수**가 한 번이라도 호출됐는가 |
| Statement Coverage | 세미콜론으로 끝나는 **개별 구문** 단위 (Line보다 세밀 — 한 줄에 구문 여러 개일 때 갈림) |

핵심은 **Line과 Branch**다. 이 둘은 다른 것을 측정하고, 하나만 보면 반드시 놓치는 게 생긴다.

## Line만 보면 놓치는 것 — 구체적으로

```kotlin
fun getDiscount(user: User): Int {
    if (user.isVip && user.orderCount > 10) {   // 1번 줄
        return 20                                // 2번 줄
    }
    return 0                                     // 3번 줄
}
```

테스트 2개만 쓰자.

- `isVip = true, orderCount = 11` → 1, 2번 줄 실행
- `isVip = false` → 1, 3번 줄 실행

**Line Coverage 100%.** 그런데 검증 안 된 케이스가 남아 있다.

| `isVip` | `orderCount > 10` | 전체 조건 | 테스트했나 |
| --- | --- | --- | --- |
| true | true | true (할인) | ✅ |
| true | false | false | ❌ **놓친 케이스** |
| false | true | false | ❌ |
| false | false | false | ✅ |

`isVip = true`인데 `orderCount = 5`인 경우 — **`&&`의 앞은 참, 뒤는 거짓** — 은 한 번도 안 돌았다.
1번 줄은 "실행됨"으로 표시되지만, 그 줄 **안에 있는 분기 중 절반은 미검증**인 채로 100%가 나온 것이다.

> **왜 이런 일이 생기나**: 한 줄에 조건이 여러 개 묶여 있으면, 줄 단위 계수기는 그 안의 갈래를 구분하지 못한다.
> 게다가 [[short-circuit|쇼트 서킷]] 때문에 `&&` 앞이 거짓이면 **뒤 조건은 평가조차 되지 않는다** —
> 실행 흔적이 애초에 안 찍히는 코드 경로가 존재한다는 뜻이다. Branch Coverage는 바로 이 갈래를 센다.

## 왜 Branch 기준을 Line보다 낮게 잡나

분기 조합 수는 조건이 겹칠수록 **기하급수적으로** 늘어난다. `&&`/`||`가 3개면 최대 8가지.
100%에 가깝게 맞추려면 테스트 작성 비용이 급격히 커지고, 어느 지점부터는 **얻는 안전성보다 비용이 커진다.**

그래서 실무 기준은 보통 이렇게 잡힌다:

> **"라인은 거의 다 지나가게(90%), 분기는 웬만큼 다양하게(80%)"**

두 지표에 **다른 임계치**를 두는 게 핵심이다.

## 왜 둘 다 봐야 하는가

- **Line만 보면** — 위 예제처럼 절반만 테스트하고도 100%로 착각한다.
- **Branch만 보면** — 분기가 거의 없는 단순 유틸(포맷터·매퍼 등)은 Branch가 애초에 의미가 적다. 이런 코드는 Line으로 충분하다.
- 그래서 두 지표를 **함께** 기준으로 삼고, **조건 분기가 많은 핵심 로직은 둘 다 100%** 를 요구한다.

## 등급을 나누는 실무 패턴

모든 코드에 같은 기준을 적용하는 건 비효율적이다. **결함의 파급력**으로 등급을 나눈다.

| 구분 | Line | Branch | 이유 |
| --- | --- | --- | --- |
| 일반 Service / Controller | 90%+ | 80%+ | 모든 분기를 다 테스트하는 비용이 이득을 넘는 지점이 있다 |
| 핵심 비즈니스 (인증·권한·감사) | 100% | 100% | 분기 하나만 놓쳐도 **"인증 우회"** 같은 심각한 결함이 된다 |

**왜 인증·권한·감사가 특별한가**: 일반 로직의 버그는 "값이 틀리게 나온다"로 끝나지만,
[[spring-security|인증·권한]] 로직의 분기 누락은 **보안 경계가 뚫리는 것**이다.
`if (token.isValid() && user.hasRole(ADMIN))`에서 두 번째 조건의 false 케이스를 테스트 안 했다면,
그건 "권한 없는 사용자가 통과하는지 확인 안 했다"와 같은 말이다.
[[jpa-auditing|감사(audit)]] 로직도 마찬가지 — 기록이 빠지면 사고를 재구성할 수 없다.

## 리포트 읽는 법 — 노란 줄

[[jacoco|JaCoCo]] HTML 리포트는 각 줄 옆을 색으로 표시한다.

| 색 | 의미 |
| --- | --- |
| 🟢 초록 | 완전히 커버됨 |
| 🔴 빨강 | 실행되지 않음 |
| 🟡 **노랑** | **실행은 됐지만 분기 중 일부만 테스트됨** |

**노랑이 이 문서의 핵심**이다. 위 예제의 1번 줄이 정확히 노란색으로 나온다 —
Line 기준으로는 100%지만 Branch 기준으로는 미완인 상태.

## 체크리스트

- [ ] 리포트에서 **노란색**(분기 일부 누락) 줄이 있는지 확인했는가 — Line 100%라고 안심하지 않았는가
- [ ] 인증·권한·감사 관련 코드가 100% 기준을 충족하는가
- [ ] 조건이 3개 이상 겹친 복잡한 `if`는 **분기를 쪼개서** 테스트 가능하게 리팩터링을 검토했는가
- [ ] 커버리지를 올리려고 `assert` 없는 호출만 늘리고 있지는 않은가

> 세 번째 항목이 흥미로운 지점이다. **커버리지 기준이 설계 압력으로 작동한다** —
> "테스트하기 어려운 코드"는 대개 "책임이 너무 많은 코드"라서, 분기를 쪼개는 리팩터링이
> [[solid-principles|SRP]]로 이어진다.

## 측정 도구

| 스택 | 도구 | 명령 | 리포트 |
| --- | --- | --- | --- |
| Java/Kotlin | **[[jacoco]]** | `./gradlew test jacocoTestReport` | `build/reports/jacoco/test/html/index.html` |
| 프론트 | **Vitest + v8** | `pnpm test:coverage` | `coverage/index.html`, `coverage/lcov.info` |

프론트는 Vitest의 v8 coverage provider로 측정하고 **lcov 리포트를 SonarQube에 연동**한다.
개념(Line/Branch)은 백엔드와 동일하고, 여기에 Function·Statement Coverage가 리포트에 추가로 나온다.

> `lcov.info`는 커버리지 리포트의 **공통 교환 포맷**이다. 언어·도구가 달라도 이 포맷으로 뱉으면
> SonarQube 같은 통합 대시보드가 한자리에서 볼 수 있다 — Java와 TS를 한 프로젝트로 묶는 방법.
