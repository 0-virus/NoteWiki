# 최종 일관성 (Eventual Consistency)

## 한 줄 정의

**변경 직후에는 시스템 간 상태가 다를 수 있지만, 시간이 지나 재시도가 성공하면
결국 같은 상태로 수렴한다는 일관성 모델.** "당장은 아니지만, 결국은."

## 왜 등장하는가

하나의 DB [[transaction]] 안에서는 강한 일관성(Strong Consistency)이 자연스럽다 — 커밋
순간 모든 변경이 즉시 반영된다. 하지만 시스템이 여러 개(내부 DB + 외부 API, 또는 여러
서버 인스턴스)로 나뉘면, 모든 시스템을 하나의 트랜잭션으로 묶을 수 없다.

[[outbox-pattern]]이 전형적인 예다.

```
10:00:00  내부 DB 변경 + Outbox 메시지 생성 (커밋 완료)
10:00:05  첫 전송 실패
10:00:15  두 번째 전송 성공 → 외부 시스템 반영
```

10:00:00 ~ 10:00:15 사이 내부 DB와 외부 시스템은 **다른 상태**다. 하지만 재시도가
성공하면 최종적으로 일치한다 — 이것이 최종 일관성이다.

## 강한 일관성과의 대비

| | 강한 일관성 | 최종 일관성 |
| --- | --- | --- |
| 대표 사례 | 단일 DB [[transaction]] | [[outbox-pattern]], 다중 서버 복제 |
| 읽기 시점 보장 | 항상 최신 값 | 한동안 오래된 값을 볼 수 있음 |
| 비용 | 락·동기화 비용 높음 | 비동기 처리 가능, 처리량↑ |
| 실패 시 | 롤백으로 즉시 원상복구 | 재시도/보정으로 서서히 수렴 |

## 한계 — 저절로 수렴하지 않는 경우

"결국은 같아진다"는 전제는 **재시도가 언젠가 성공한다**는 가정 위에 있다. 영구적인
데이터 오류나 계약 불일치(예: 필드 누락, 잘못된 스키마)가 있으면 자동으로 수렴하지
않는다. 이때는 원인을 수정하고 수동으로 재처리하거나 별도 보정이 필요하다 —
[[outbox-pattern]]의 `FAILED` 상태가 이 지점을 위한 장치다.

## 영균 학습 트리에서

지금까지 배운 [[transaction]]의 ACID는 **하나의 DB 안**에서의 즉시 일관성 이야기였다.
[[outbox-pattern]]을 만나며 처음으로 "DB 밖 시스템과는 즉시 일치를 포기하고, 대신
추적·재시도 가능하게 만든다"는 다른 종류의 일관성 모델을 마주하게 된 것.
