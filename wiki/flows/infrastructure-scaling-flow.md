# 3-Tier·CI·HCI에서 자원 부족과 장애 여유를 판단하는 흐름

## 1. 어떤 자원이 부족한지 확인한다

[[data-center|IDC]] 안의 서버 세 대가 각각 CPU 32코어, RAM 128GB, 데이터용 SSD 2TB를 가진다고 가정한다. [[hyperconverged-infrastructure|HCI]]의 노드 A에서 [[spring-boot|Spring Boot]]가 8 vCPU·RAM 32GB [[virtual-machine|VM]]으로 동작하고, 가상 디스크는 [[software-defined-storage|SDS]]가 두 노드에 전체 사본을 유지한다.

API 요청은 [[network-virtualization|물리망과 가상망]]을 거쳐 VM에 도착한다. 코드는 노드 A의 CPU에서 실행되고, VM의 작업 메모리도 그 호스트에서 사용한다. 디스크 쓰기는 SDS가 받아 정책에 따라 여러 노드에 배치한다. **VM의 실행 위치와 디스크 사본의 저장 위치를 따로 그리면, 어느 자원이 병목인지 구분할 수 있다.**

## 2. 증설 단위를 수요에 맞춘다

| 상황 | 3-Tier·CI에서 보는 것 | HCI에서 보는 것 |
| --- | --- | --- |
| 저장 공간만 부족 | 별도 스토리지에 디스크나 용량을 추가할 수 있는지, CI에서는 검증된 조합인지 | 디스크 추가나 스토리지 전용 노드가 가능한지, 일반 노드 추가 시 따라오는 컴퓨팅 비용 |
| CPU·RAM만 부족 | 컴퓨팅 서버를 추가할 수 있는지, CI에서는 검증된 구성인지 | 기존 호스트 증설 또는 컴퓨팅 전용 노드 지원 여부, 큰 VM을 수용할 개별 호스트의 여유 |
| 컴퓨팅과 저장 공간이 함께 부족 | 두 계층의 확장량을 각각 산정 | 일반 노드 한 대가 제공하는 CPU·RAM·디스크 비율이 수요와 맞는지 |

[[horizontal-vs-vertical-scaling|수평·수직 확장]]은 증설 방법을 설명한다. HCI에서는 노드를 추가해도 개별 VM 한 대가 여러 호스트의 RAM을 합쳐 쓰지는 않으므로, 큰 VM의 메모리 요구는 호스트 단위로 계산한다.

## 3. 노드가 빠진 뒤의 여유를 다시 계산한다

| 계산 | 세 노드 정상 | 한 노드 장애 |
| --- | --- | --- |
| 물리 CPU·RAM 합계 | 96코어, 384GB | 64코어, 256GB |
| 데이터용 원시 용량 | 6TB | 4TB |
| 서로 다른 노드에 사본 2개를 유지할 때의 이론 용량 | 약 3TB | 약 2TB |

위 값은 관리 서비스, 메타데이터, 배치 제약과 재구축 여유를 빼기 전이다. 예를 들어 VM 합계가 RAM 280GB면 세 노드에서는 합계 기준으로 여유가 있어 보이지만, 한 노드가 빠지면 남은 RAM 256GB에 모두 배치할 수 없다. 사용자 데이터 2.5TB도 정상 상태의 단순 복제 계산에는 들어가지만, 같은 복제 정책을 두 노드에서 완전히 복구하기에는 공간이 부족하다. 저장 공간이 남더라도 복구 가능 여부는 생존 사본, 쓰기 허용 조건, [[infrastructure-cluster|클러스터 정족수]]에 좌우된다.

## 4. 점검과 장애 뒤의 서비스 상태를 확인한다

- **계획 점검**에서는 살아 있는 노드 A의 실행 상태를 [[live-migration|라이브 마이그레이션]]으로 B나 C에 옮길 수 있다. 대상의 여유 자원, 네트워크, 스토리지 접근 조건이 필요하다.
- **갑작스러운 고장**에서는 [[high-availability|VM HA]]가 안전한 전환과 가상 디스크 접근 조건을 확인하고 다른 노드에서 VM을 부팅한다. 앱이 다시 요청을 받을 때까지 중단될 수 있다. VM과 별도로 [[load-balancer|로드 밸런서]]의 백엔드 상태와 실제 API 응답을 확인하면 서비스가 복구됐는지 판단할 수 있다.

위 과정은 물리 자원을 운영하는 방법이다. 사용자가 포털에서 VM을 직접 요청·반납하고 사용량을 확인하는 제공 방식은 [[cloud-computing|클라우드 컴퓨팅]]에서 설명한다.
