## 1. 전체 개념 지도

먼저 각 용어가 답하는 질문부터 구분한다.

| 구분 | 핵심 질문 | 관련 개념 |
| --- | --- | --- |
| 시설 | 장비를 어디에서 안정적으로 운영하는가? | IDC, 데이터센터 |
| 하드웨어 | 무엇으로 계산하고 데이터를 보관하는가? | CPU, RAM, SSD/HDD, 네트워크 장비 |
| 인프라 아키텍처 | 서버·스토리지·네트워크를 어떻게 구성하는가? | 3-Tier, CI, HCI |
| 자원 추상화 | 물리 자원을 어떻게 나누거나 묶어 사용하는가? | 하이퍼바이저, VM, SDS, 네트워크 가상화 |
| 공동 운영 | 여러 서버의 배치·장애·확장을 어떻게 관리하는가? | 클러스터, HA, 라이브 마이그레이션 |
| 서비스 제공 | 사용자에게 자원을 어떤 방식으로 제공하는가? | 클라우드 컴퓨팅 |

```text
IDC / 데이터센터: 전력·냉각·통신·보안 등 운영 기반
└─ IT 인프라: 3-Tier, CI, HCI 등의 구성 방식을 선택
   └─ HCI를 선택한 경우의 일반적인 구성
      ├─ 여러 물리 서버를 클러스터로 운영
      ├─ 하이퍼바이저로 VM 실행
      ├─ SDS로 여러 노드의 저장장치를 통합 관리
      ├─ 물리·가상 네트워크로 자원과 서비스 연결
      └─ 통합 관리 도구로 배치·상태·용량 관리

이 기반에 셀프서비스·자동화·사용량 측정 등을 더하면
프라이빗 클라우드 구현에 활용할 수 있다.
```

**IDC는 장소와 시설, HCI는 인프라 구성 방식, 클라우드는 자원 제공 방식이다.** 서로 대체하는 같은 종류의 용어가 아니다.

## 2. IDC: 인프라가 운영되는 장소

**IDC(Internet Data Center, 인터넷 데이터센터)**는 서버와 네트워크 장비 등을 안정적으로 운영할 수 있도록 마련된 시설이다. 국내에서는 인터넷 서비스와 기업 시스템을 수용하는 데이터센터를 가리킬 때 흔히 사용한다.

| 구성 요소 | 역할 |
| --- | --- |
| 서버·스토리지·네트워크 | 애플리케이션 실행, 데이터 저장, 통신 |
| 랙과 설치 공간 | 장비 배치와 케이블 관리 |
| 전력 설비 | 전력 공급, UPS·발전기 등을 통한 정전 대비 |
| 냉각 설비 | 장비의 열을 제거하고 적절한 환경 유지 |
| 통신 회선 | 인터넷·사내망·다른 데이터센터 연결 |
| 물리 보안·관제 | 출입 통제, 상태 감시, 장애 대응 |

기업은 자체 데이터센터를 운영하거나, 외부 IDC의 공간·전력·회선을 이용할 수 있다. 자체 장비를 외부 시설에 설치하는 방식은 **코로케이션(colocation)**이라고 한다. 데이터센터 시설과 운영 형태는 [IBM의 데이터센터 설명](https://www.ibm.com/think/topics/data-centers)을 참고할 수 있다.

예를 들어 “IDC에 HCI를 구축했다”는 말은 **데이터센터 시설 안에 HCI 방식의 IT 인프라를 설치했다**는 뜻이다. 하나의 IDC 안에 3-Tier와 HCI가 함께 존재할 수도 있다.

## 3. CPU·RAM·스토리지: 서버의 기본 자원

### 3.1 역할 비교

| 항목 | CPU | RAM | SSD/HDD |
| --- | --- | --- | --- |
| 뜻 | 중앙처리장치 | 주기억장치 | 보조기억장치 |
| 핵심 역할 | 명령 실행과 연산 | 실행 중인 프로그램·데이터 보관 | 프로그램·데이터의 장기 저장 |
| 비유 | 일하는 사람 | 작업 중 자료를 펼쳐 놓는 책상 | 자료를 보관하는 서랍 |
| 주요 지표 | 코어 수, 클럭, IPC | 용량, 대역폭, 지연시간 | 용량, IOPS, 처리량, 지연시간 |
| 부족할 때 | 계산·요청 처리 지연 | 메모리 회수·스와핑, 실행 실패 | 저장 공간 부족, 읽기·쓰기 지연 |

일반적인 서버 RAM은 전원을 끄면 내용이 사라지는 **휘발성 메모리**다. SSD/HDD에 정상적으로 기록된 데이터는 전원이 꺼져도 유지된다.

- **코어(Core)**: CPU 안에서 명령을 실행하는 처리 단위.
- **클럭(GHz)**: 동작 주파수. 클럭만으로 서로 다른 CPU의 성능을 단정할 수 없다.
- **IPC**: 클럭 한 주기당 처리하는 명령 수. CPU 구조와 작업에 따라 달라진다.
- **IOPS**: 초당 처리하는 입출력 작업 수. 작업 크기와 접근 방식도 함께 봐야 한다.
- **스와핑(Swapping)**: 메모리의 일부 내용을 저장장치로 옮겨 공간을 확보하는 동작. RAM 접근보다 느려 성능에 큰 영향을 줄 수 있다.

### 3.2 프로그램 실행 예시

Spring Boot 애플리케이션을 실행한다고 가정하자.

```text
SSD: JAR 파일·설정·저장 데이터 보관
  ↓ 프로그램과 필요한 데이터를 읽음
RAM: JVM·객체·Heap·실행 중 데이터 보관
  ↕ 명령과 데이터 접근
CPU: 코드 실행·계산·API 요청 처리
  ↓ 저장이 필요한 결과
SSD 또는 데이터베이스 등 영속 저장소에 기록
```

암호화나 계산 작업이 많으면 CPU가, 캐시나 큰 JVM Heap을 사용하면 RAM이 중요하다. 저장장치 입출력이나 네트워크가 병목일 수도 있으므로, 느리다는 이유만으로 CPU나 RAM부터 늘리는 것은 적절하지 않다.

## 4. 가상화: 하이퍼바이저·VM·vCPU

### 4.1 가상화란?

**가상화(Virtualization)**는 물리 자원을 소프트웨어로 추상화하여 논리적인 자원이나 실행 환경으로 제공하는 기술이다. 서버 가상화에서는 한 물리 서버에서 여러 운영체제를 각각 독립된 VM으로 실행할 수 있다.

### 4.2 하이퍼바이저와 VM

- **호스트(Host)**: VM이 실행되는 물리 서버를 가리킨다.
- **하이퍼바이저(Hypervisor)**: VM을 실행하고 CPU·메모리 등의 자원 배분과 격리를 관리하는 소프트웨어 계층이다.
- **VM(Virtual Machine, 가상머신)**: 가상 CPU·메모리·디스크·네트워크 장치를 가진 논리적인 컴퓨터다.
- **게스트 OS(Guest OS)**: VM 안에서 실행되는 운영체제다.

```text
물리 서버: CPU 32코어 / RAM 128GB
└─ 하이퍼바이저
   ├─ VM 1: Linux   / 8 vCPU / RAM 32GB
   ├─ VM 2: Linux   / 8 vCPU / RAM 32GB
   └─ VM 3: Windows / 4 vCPU / RAM 16GB
```

예시의 VM 메모리 설정 합계는 80GB다. 남은 자원은 다른 VM뿐 아니라 하이퍼바이저·관리 서비스·SDS 등의 운영에도 필요하다. HCI에서는 사용자 VM 이외의 자원 사용량도 고려해야 한다.

하이퍼바이저는 흔히 물리 하드웨어 위에서 동작하는 **Type 1**과 일반 호스트 OS 위에서 애플리케이션처럼 동작하는 **Type 2**로 구분한다. 서버 환경에는 ESXi, Hyper-V, KVM 기반 플랫폼 등이 사용된다. Hyper-V의 하드웨어 가상화와 VM 실행 역할은 [Microsoft 공식 개요](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/overview)에 설명되어 있다.

### 4.3 vCPU는 물리 코어와 무엇이 다른가?

**vCPU(virtual CPU)**는 VM에 제공되는 가상 프로세서다. 일반적으로 하이퍼바이저가 물리 CPU의 실행 자원에 vCPU를 스케줄링한다.

| 용어 | 의미 |
| --- | --- |
| 물리 CPU 패키지 | 서버의 CPU 소켓에 장착하는 실제 프로세서 |
| 물리 코어 | CPU 내부의 실제 처리 단위 |
| 논리 프로세서 | 운영체제나 하이퍼바이저가 스케줄링 대상으로 인식하는 하드웨어 실행 단위 |
| vCPU | VM에 노출되는 가상 프로세서 |

SMT를 사용하는 CPU는 하나의 물리 코어를 여러 논리 프로세서로 노출할 수 있다. 다만 논리 프로세서 수가 두 배라고 실제 계산 성능도 두 배가 되는 것은 아니다.

**8 vCPU를 할당했다고 물리 코어 8개를 항상 독점하는 것은 아니다.** 전용 할당이나 고정 배치 정책이 없다면 다른 VM과 CPU 실행 시간을 공유할 수 있다. 구현 예시는 [Microsoft의 가상 프로세서 스케줄링 설명](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/manage/manage-hyper-v-scheduler-types)을 참고한다.

### 4.4 오버커밋과 자원 부족

**오버커밋(Overcommit)**은 가상 자원의 할당 합계를 실제 물리 자원보다 크게 설정하는 것이다. 모든 VM이 동시에 최대 자원을 사용하지 않는다는 특성을 활용한다.

- **CPU**: 여러 VM에 실행 시간을 나누어 줄 수 있다. 모든 VM이 동시에 바빠지면 대기 시간이 늘어난다.
- **RAM**: 실제 작업 데이터가 머물 공간이 필요하다. 제품에 따라 동적 할당·메모리 회수·스와핑 등을 사용할 수 있지만, 과도한 할당은 큰 성능 저하나 실행 실패를 일으킨다.

vCPU를 많이 주는 것만으로 성능이 보장되지는 않는다. 애플리케이션의 병렬 처리 능력과 물리 서버의 여유 자원도 중요하다.

## 5. 클러스터: 여러 서버를 함께 운영하는 구조

**클러스터(Cluster)**는 여러 컴퓨터가 협력하여 서비스를 제공하거나 자원을 공동 관리하도록 구성한 집합이다. 구성원 하나를 **노드(Node)**라고 한다. HCI에서는 보통 물리 서버 한 대가 하나의 노드다.

| 목적 | 동작 예시 |
| --- | --- |
| 통합 관리 | 여러 노드의 상태와 자원을 한곳에서 확인 |
| 부하 분산 | VM을 여러 노드에 배치하거나 이동 |
| 고가용성 | 장애가 난 노드의 VM을 정상 노드에서 재시작 |
| 확장 | 노드를 추가하여 전체 처리 용량 증가 |

이 기능들이 클러스터라는 이름만으로 자동 제공되는 것은 아니다. 제품과 설정에 따라 지원 범위가 달라진다.

### CPU와 RAM이 하나로 합쳐지는가?

다음과 같이 세 노드가 있다고 하자.

```text
노드 A: CPU 32코어 / RAM 128GB
노드 B: CPU 32코어 / RAM 128GB
노드 C: CPU 32코어 / RAM 128GB
--------------------------------
클러스터의 물리 자원 합계: 96코어 / RAM 384GB
```

이는 **배치 가능한 전체 자원의 합계**다. 일반적인 VM은 한 시점에 하나의 호스트에서 실행된다. 따라서 VM 하나가 세 서버의 RAM을 모아 곧바로 300GB 메모리를 사용하는 것은 아니다. 클러스터 전체 여유량뿐 아니라 VM을 실행할 개별 호스트의 수용 능력도 확인해야 한다.

여러 서버에 걸쳐 하나의 작업을 처리하려면 애플리케이션 자체가 분산 처리를 지원하는 등 별도의 구성이 필요하다.

## 6. SDS: 소프트웨어로 관리하는 스토리지

### 6.1 SDS의 정확한 의미

**SDS(Software-Defined Storage, 소프트웨어 정의 스토리지)**는 저장 기능과 관리 정책을 특정 저장장치 하드웨어로부터 분리하여 소프트웨어 중심으로 제공하는 방식이다.

HCI에서 사용하는 분산 SDS는 여러 노드의 SSD/HDD를 논리적인 스토리지 풀로 묶고, 데이터 배치·보호·복구 등을 관리한다. **SDS 전체가 HCI 전용인 것은 아니며**, 별도 스토리지 서버들에 구축할 수도 있다.

스토리지 가상화는 저장장치를 논리적인 자원으로 추상화하는 데 초점이 있고, SDS는 저장 서비스와 정책을 소프트웨어로 제어하는 더 넓은 개념이다. 두 용어를 완전히 같은 뜻으로 사용하지 않는 편이 정확하다. [Red Hat의 SDS 설명](https://www.redhat.com/en/topics/data-storage/software-defined-storage)

### 6.2 HCI의 분산 SDS가 하는 일

- 여러 디스크를 논리적인 저장 공간으로 제공한다.
- 데이터를 노드와 디스크에 분산 배치한다.
- 복제나 이레이저 코딩 등으로 장애에 대비한다.
- 장애 후 데이터 보호 수준을 회복하도록 재구축한다.
- 장비 추가 시 데이터를 재배치할 수 있다.

**이레이저 코딩(Erasure Coding)**은 데이터를 여러 조각과 복구용 정보로 나누어 저장하는 방식이다. 전체 사본을 여러 개 두는 복제와 용량 효율·처리 비용이 다르다.

### 6.3 물리 용량과 실제 사용 가능 용량

노드마다 데이터 저장용 SSD가 2TB씩 있다면 세 노드의 **원시 용량(Raw Capacity)** 합계는 6TB다.

```text
노드 A: 2TB + 노드 B: 2TB + 노드 C: 2TB = 원시 용량 6TB

전체 사본을 2개 유지하는 단순 복제 가정:
6TB ÷ 2 = 사용자 데이터 약 3TB

전체 사본을 3개 유지하는 단순 복제 가정:
6TB ÷ 3 = 사용자 데이터 약 2TB
```

위 계산은 메타데이터, 시스템 사용량, 장애 복구용 여유 공간 등을 제외한 이론적인 계산이다. 압축·중복 제거 효과도 가정하지 않았다. 따라서 “SSD 합계 6TB이므로 파일도 6TB 저장할 수 있다”라고 단정하면 안 된다. 복제 수를 저장 정책으로 지정하는 예시는 [Ceph의 풀 문서](https://docs.ceph.com/en/latest/rados/operations/pools/)에서 확인할 수 있다.

장애 대응은 사본 개수만으로 결정되지 않는다. 사본이 서로 다른 노드나 랙에 배치되는지, 필요한 데이터와 서비스가 살아 있는지, 쓰기 허용 조건과 정족수가 충족되는지까지 중요하다.

## 7. HCI: 컴퓨팅과 스토리지를 통합하는 아키텍처

**HCI(Hyper-Converged Infrastructure, 하이퍼컨버지드 인프라)**는 일반적으로 서버의 컴퓨팅 자원과 로컬 저장장치를 소프트웨어로 결합하고, 여러 노드를 통합 운영하는 인프라 아키텍처다. [Nutanix의 HCI 개요](https://www.nutanix.com/hyperconverged-infrastructure)

| 구성 요소 | 역할 |
| --- | --- |
| 물리 노드 | CPU·RAM·SSD/HDD·네트워크 인터페이스 제공 |
| 하이퍼바이저 | VM 실행과 자원 배분 |
| 분산 SDS | 저장장치 통합, 데이터 배치와 보호 |
| 클러스터 관리 | 노드 상태·VM 배치·장애 대응 관리 |
| 통합 관리 도구 | VM·스토리지·정책·상태를 함께 운영 |
| 물리·가상 네트워크 | VM 통신과 노드 간 데이터 전달 |

```text
                    통합 관리
                        │
       ┌────────────────┼────────────────┐
       │                │                │
     노드 A           노드 B           노드 C
    VM 1, 2          VM 3, 4          VM 5, 6
   하이퍼바이저      하이퍼바이저      하이퍼바이저
     SDS 구성요소      SDS 구성요소      SDS 구성요소
   CPU/RAM/SSD      CPU/RAM/SSD      CPU/RAM/SSD
       │                │                │
       └────────── 물리 네트워크 ──────────┘
                        │
          SDS가 제공하는 논리적 스토리지 풀
```

이 그림은 역할을 구분한 개념도다. SDS는 제품에 따라 호스트 내부 서비스나 별도 컨트롤러 VM 등으로 구현된다. 스토리지 풀이 실제로 한 장비에 모여 있다는 뜻은 아니다.

**핵심은 컴퓨팅과 스토리지의 통합 운영이다.** 하이퍼바이저만 설치한 서버나 서버 여러 대를 연결한 구성만으로 HCI가 되는 것은 아니다. 또한 HCI에서도 노드 간 통신을 위한 물리 스위치와 네트워크 설계가 필요하다.

## 8. 3-Tier·CI·HCI 비교

### 8.1 여기서 말하는 3-Tier

이 문서의 **3-Tier**는 컴퓨팅·스토리지 네트워크·외장 스토리지로 구성되는 전통적인 인프라 구조를 뜻한다. 애플리케이션의 **웹–애플리케이션–DB 3계층**이나 네트워크의 **코어–분배–액세스 3계층**과 구분해야 한다.

```text
3-Tier: 서버 ── 스토리지 네트워크 ── 외장 스토리지
        구성 요소를 선택하고 통합하여 운영

CI:     [서버 + 네트워크 + 외장 스토리지]
        사전 검증한 조합 또는 패키지로 제공

HCI:    [컴퓨팅 + 로컬 디스크] 노드 여러 대
        가상화·SDS·통합 관리로 운영
```

**CI(Converged Infrastructure, 컨버지드 인프라)**는 서버·스토리지·네트워크 등 별도의 구성 요소를 사전에 검증하고 통합해 제공하는 방식이다. 완제품 패키지뿐 아니라 검증된 참조 아키텍처 형태로도 제공된다. [Cisco의 CI 설명](https://www.cisco.com/site/us/en/learn/topics/computing/what-is-converged-infrastructure.html)

### 8.2 주요 차이

| 항목 | 3-Tier | CI | HCI |
| --- | --- | --- | --- |
| 중심 개념 | 구성 요소를 분리하여 설계 | 장비 조합을 사전 검증·통합 | 컴퓨팅·스토리지를 소프트웨어로 통합 |
| 일반적인 스토리지 | 별도 SAN/NAS 장비 | 검증된 외장 스토리지 | 노드의 로컬 디스크와 분산 SDS |
| 관리 | 계층별 도구 중심, 통합 도구도 가능 | 통합 수준이 제품마다 다름 | VM·스토리지·클러스터 통합 관리 중심 |
| 확장 | 컴퓨팅·스토리지를 각각 확장 | 검증된 구성 범위에서 확장 | 노드 추가 중심, 제품별 자원 독립 확장도 가능 |
| 주요 장점 | 구성과 자원별 확장의 유연성 | 호환성 검증과 구축 부담 감소 | 운영 표준화와 클러스터 확장 편의 |
| 검토할 점 | 통합 설계·운영의 복잡성 | 검증 범위와 공급업체 의존성 | 라이선스, 자원 비율, 장애 시 여유 용량 |

**SAN(Storage Area Network)**은 서버에 블록 단위 저장장치 접근을 제공하는 전용 목적의 네트워크다. **NAS(Network Attached Storage)**는 NFS·SMB 같은 프로토콜로 파일 단위 접근을 제공하는 저장 시스템이다. SAN은 네트워크 개념이므로 “SAN”과 “스토리지 장비”가 엄밀히 같은 말은 아니다.

### 8.3 확장 상황으로 이해하기

| 상황 | 3-Tier / CI | HCI |
| --- | --- | --- |
| CPU·RAM이 부족 | 컴퓨팅 서버 추가 또는 지원 범위 내 증설 | 노드 추가나 지원되는 컴퓨팅 자원 증설 |
| 저장 공간만 부족 | 스토리지 용량을 별도로 확장 | 디스크·스토리지 노드·일반 노드 등 지원 방식 확인 |
| 서버 점검 필요 | 가상화 클러스터가 있다면 VM 이동 가능 | 지원 조건을 만족하면 VM 이동 가능 |

HCI는 자원 수요가 균형 있게 늘어날 때 확장 계획을 단순화할 수 있다. 반면 저장 공간만 크게 늘어나는 상황에서는 컴퓨팅 자원까지 구매하게 되는지 확인해야 한다. **실제 선택은 성능, 가용성, 기존 장비, 운영 역량, 전체 비용을 함께 비교해야 한다.** HCI가 항상 더 빠르거나 저렴한 것은 아니다.

## 9. 네트워크 가상화

**네트워크 가상화**는 물리 네트워크 위에서 논리적인 연결과 분리된 네트워크를 제공하는 기술이다.

| 구성 요소 | 역할 |
| --- | --- |
| vNIC | VM에 제공하는 가상 네트워크 인터페이스 |
| 가상 스위치 | VM 간 또는 VM과 외부 네트워크 사이의 통신 연결 |
| VLAN | 하나의 물리 네트워크에서 논리적인 2계층 네트워크 분리 |
| VXLAN | IP 네트워크 위에 가상 2계층 네트워크를 구성하는 오버레이 기술 |
| 가상 라우터·방화벽 | 논리 네트워크 사이의 경로와 접근 정책 처리 |

```text
VM의 vNIC → 가상 스위치 → 물리 NIC → 물리 스위치 → 다른 서버/외부망
```

동일 호스트의 VM끼리 통신하면 구성에 따라 물리 스위치까지 나가지 않을 수도 있다. 하지만 서로 다른 노드의 VM 통신, 스토리지 복제, 라이브 마이그레이션에는 물리 네트워크 성능과 안정성이 중요하다.

**SDN(Software-Defined Networking)**은 네트워크의 제어와 정책 적용을 소프트웨어로 관리하는 접근이다. 네트워크 가상화와 관련이 깊지만 같은 뜻은 아니다. 기본적인 가상 스위치를 사용한다고 항상 고급 SDN 플랫폼을 구축한 것은 아니다.

HCI의 관리·VM 서비스·스토리지·이동 트래픽은 목적에 맞게 분리하거나 대역폭을 관리할 수 있다. VLAN으로 구분하더라도 같은 물리 링크를 사용하면 대역폭은 공유한다. 클러스터 트래픽 종류와 대역폭 고려사항은 [Microsoft의 클러스터 네트워크 문서](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/failover-cluster-network-recommendations)에 정리되어 있다.

## 10. HA와 라이브 마이그레이션

### 10.1 HA: 장애 후 서비스를 복구

**HA(High Availability, 고가용성)**는 장애가 발생해도 서비스 중단을 줄이기 위한 설계와 기능을 통칭한다. 여기서는 **호스트 장애 시 다른 노드에서 VM을 재시작하는 일반적인 가상화 HA**를 중심으로 설명한다.

```text
노드 A에서 VM 실행
  → 노드 A 장애
  → 클러스터가 장애 감지 및 안전한 전환 여부 판단
  → 노드 B에서 해당 VM 재시작
  → 게스트 OS와 애플리케이션 복구
```

재시작 시간이 필요하므로 서비스 중단이 발생할 수 있다. 장애 순간 RAM에만 존재하던 상태는 일반적인 VM 재시작 방식으로 그대로 복구되지 않는다.

HA가 동작하려면 정상 노드에 충분한 CPU·RAM이 있어야 하고, VM 구성과 디스크에 접근할 수 있어야 한다. 데이터 보호 정책, 장애 감지, 정족수와 중복 실행 방지 설정도 필요하다.

**정족수(Quorum)**는 장애나 통신 단절 상황에서 어느 쪽이 운영을 계속할지 판단하는 데 사용하는 합의 조건이다. 양쪽이 동시에 자신을 정상 시스템으로 판단하는 분리 뇌(split-brain) 문제를 방지하기 위한 설계에 사용된다.

### 10.2 라이브 마이그레이션: 실행 중인 VM을 이동

**라이브 마이그레이션(Live Migration)**은 실행 중인 VM의 메모리와 실행 상태 등을 다른 호스트로 옮겨 서비스 중단을 최소화하는 기술이다.

일반적인 방식에서는 VM이 동작하는 동안 메모리를 복사하고, 마지막 전환 때 잠깐 실행을 멈춘 뒤 대상 호스트에서 이어서 실행한다. “라이브”라고 해서 모든 조건에서 중단 시간이 절대 0이라는 뜻은 아니다. 라이브 마이그레이션의 기본 동작 목적은 [Microsoft의 공식 설명](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/failover-cluster-network-recommendations)을 참고한다.

### 10.3 두 기능 비교

| 항목 | 일반적인 VM HA | 라이브 마이그레이션 |
| --- | --- | --- |
| 주된 상황 | 호스트의 갑작스러운 장애 | 계획된 점검, 자원 재배치 |
| 원래 호스트 | 장애 상태일 수 있음 | 이동에 협력할 수 있는 정상 상태 필요 |
| 처리 방식 | 다른 호스트에서 VM 재시작 | 실행 상태를 옮겨 이어서 실행 |
| 서비스 영향 | 재부팅과 애플리케이션 복구 동안 중단 가능 | 중단 최소화, 짧은 전환 정지 가능 |
| 핵심 조건 | 여유 자원, 디스크 접근, 장애 판단과 보호 설정 | 호환성, 대상 자원, 네트워크, 스토리지 조건 |

갑자기 전원이 꺼진 서버에서 VM을 라이브 마이그레이션할 수는 없다. 해당 서버가 메모리와 실행 상태를 전달할 수 없기 때문이다.

공유 스토리지를 사용하면 VM 실행 호스트를 옮겨도 디스크 데이터 자체는 이동하지 않을 수 있다. 공유 스토리지가 없는 환경에서는 디스크도 함께 옮기는 방식이 제품에 따라 지원된다.

이 기능들은 HCI에만 있는 것이 아니다. 전통적인 가상화 클러스터에서도 제공할 수 있다. 또한 **VM이 실행 중이라는 사실과 애플리케이션이 정상 서비스 중이라는 사실은 다르다.** 애플리케이션 수준의 상태 확인과 이중화가 별도로 필요할 수 있다.

### 10.4 복제·스냅샷·백업도 구분하기

| 기능 | 주된 목적 | 기억할 점 |
| --- | --- | --- |
| 데이터 복제 | 디스크·노드 장애에 대비 | 삭제나 잘못된 변경도 복제될 수 있음 |
| 스냅샷 | 특정 시점 상태를 보존하여 되돌리기 | 원본 스토리지와 장애 범위를 공유할 수 있음 |
| 백업 | 보존한 복사본에서 데이터 복구 | 보존 기간, 격리, 복구 검증이 중요 |
| 재해 복구(DR) | 사이트 장애 등 큰 장애에서 서비스 복구 | 별도 위치의 데이터·실행 환경·복구 절차 필요 |

VM 스냅샷에 메모리가 포함되는지는 제품과 설정에 따라 다르다. **복제와 로컬 스냅샷만으로 독립적인 백업을 대신할 수 있다고 가정해서는 안 된다.**

## 11. 하나의 예시로 이해하는 HCI 동작

### 11.1 구성 가정

- 노드 A·B·C는 각각 CPU 32코어, RAM 128GB, 데이터 저장용 SSD 2TB를 가진다.
- VM 1은 노드 A에서 실행되며 8 vCPU와 RAM 32GB를 할당받는다.
- VM의 가상 디스크는 SDS가 제공하는 논리적 스토리지에 놓인다.
- 저장 데이터는 서로 다른 노드에 전체 사본 2개를 유지하도록 설정했다고 가정한다.
- 이 예시는 학습용이며 특정 제품의 권장 구성이나 장애 허용 보장을 뜻하지 않는다.

### 11.2 API 요청과 데이터 저장

1. 사용자의 요청이 물리 네트워크와 가상 네트워크를 거쳐 VM 1에 도착한다.
2. VM의 게스트 OS와 애플리케이션이 요청을 처리한다.
3. vCPU의 작업은 노드 A의 물리 CPU에서 실행되고, 작업 데이터는 해당 호스트의 RAM에 놓인다.
4. 애플리케이션이 저장을 요청하면 가상 디스크 입출력이 스토리지 계층에 전달된다.
5. SDS가 정책에 따라 실제 디스크 위치와 복제 배치를 관리한다. 예를 들어 A와 B에 사본이 저장될 수 있다.
6. 저장 완료를 알리는 조건은 복제 방식과 제품의 쓰기 정책에 따라 결정된다.

VM의 **실행 위치**와 디스크 데이터의 **물리 저장 위치**는 같은 개념이 아니다.

### 11.3 노드 A를 점검하는 경우

노드 A가 정상이라면 VM 1을 B나 C로 라이브 마이그레이션한 뒤 점검할 수 있다. 대상 노드의 여유 자원과 네트워크·스토리지 접근 조건을 먼저 충족해야 한다.

### 11.4 노드 A가 갑자기 고장 난 경우

살아 있는 노드에서 VM의 디스크에 접근할 수 있고 HA 조건이 충족된다면 다른 노드에서 VM 1을 재시작한다. 이 과정에서 서비스 중단이 발생하며, SDS는 필요에 따라 데이터의 보호 수준을 다시 회복한다.

한 노드의 장애에도 전체 VM을 운영하려면 남은 두 노드의 자원으로 작업을 수용할 수 있어야 한다. 따라서 평상시 세 노드의 용량을 전부 채워 사용하는 설계는 장애 시 문제가 될 수 있다.

## 12. HCI와 클라우드의 관계

### 12.1 관점의 차이

| 개념 | 관점 | 예시 |
| --- | --- | --- |
| 가상화 | 물리 자원을 추상화하는 기술 | VM 생성 |
| HCI | 인프라 자원을 통합하는 아키텍처 | 컴퓨팅·SDS를 결합한 클러스터 |
| 클라우드 | 자원을 요청·사용·반납하게 하는 서비스 모델 | 사용자가 포털에서 VM을 생성하고 사용량 확인 |

클라우드 컴퓨팅은 필요할 때 네트워크를 통해 공유 자원을 빠르게 공급받고 반납할 수 있는 모델이다. NIST는 다음 다섯 가지 핵심 특성을 설명한다. [NIST SP 800-145](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-145.pdf)

| 특성 | 쉬운 설명 |
| --- | --- |
| 주문형 셀프서비스 | 사용자 스스로 필요한 자원을 요청·생성 |
| 폭넓은 네트워크 접근 | 표준 방식으로 다양한 단말에서 접근 |
| 자원 풀링 | 공유 자원을 수요에 따라 배분 |
| 신속한 탄력성 | 수요에 맞춰 자원을 빠르게 늘리거나 줄임 |
| 측정 가능한 서비스 | 사용량을 측정·관리·보고 |

사용량 측정은 반드시 외부 고객에게 요금을 청구한다는 뜻은 아니다. 사내 부서별 사용량 관리에도 활용할 수 있다.

### 12.2 HCI가 프라이빗 클라우드의 기반이 되는 과정

```text
HCI 기반 자원
  + 사용자 포털/API
  + 자동 생성·변경·반납
  + 권한·할당량·정책
  + 사용량 측정·모니터링
  → 프라이빗 클라우드 구현에 활용
```

**HCI만 설치했다고 자동으로 클라우드가 되는 것은 아니다.** 반대로 클라우드 구현에 HCI가 반드시 필요한 것도 아니다. 다른 인프라 구성 위에서도 클라우드를 구현할 수 있다.

**프라이빗 클라우드**는 한 조직 전용으로 제공되는 클라우드다. 조직 내부 시설뿐 아니라 외부 시설에서 운영할 수도 있다. **퍼블릭 클라우드**는 제공자가 일반 고객에게 이용 가능하게 제공한다. **하이브리드 클라우드**는 서로 구분되는 클라우드 환경을 연결하여 데이터나 애플리케이션의 이동·연계를 지원하는 구성이다. 이 배포 모델 구분 역시 [NIST 정의](https://csrc.nist.gov/pubs/sp/800/145/final)에 따른다.

HCI를 사용하면서 퍼블릭 클라우드를 함께 이용할 수 있다. 다만 두 환경을 보유한 것만으로 통합 운영이나 자유로운 워크로드 이동이 자동으로 이루어지는 것은 아니다.

## 13. 자주 혼동하는 내용

| 오해 | 정확한 이해 |
| --- | --- |
| IDC와 HCI 중 하나를 선택한다 | IDC는 시설이고 HCI는 그 안에 구축할 수 있는 인프라 방식이다. |
| 3-Tier는 항상 웹–애플리케이션–DB다 | 인프라 문맥에서는 컴퓨팅·스토리지 네트워크·스토리지를 의미할 수 있다. |
| VM 8 vCPU는 물리 코어 8개 독점이다 | 일반적으로 스케줄링을 통해 물리 실행 자원을 공유한다. |
| 클러스터의 RAM을 VM 하나가 모두 쓴다 | 일반적인 VM은 한 호스트의 자원 범위에서 실행된다. |
| SDS는 단순히 디스크 용량을 더하는 기술이다 | 데이터 배치와 보호 등 저장 서비스·정책을 소프트웨어로 제어한다. |
| 원시 용량 6TB는 사용자 용량 6TB다 | 복제, 메타데이터, 복구 여유 공간 등을 고려해야 한다. |
| HCI에는 물리 네트워크가 필요 없다 | 노드 통신·복제·외부 서비스 연결에 필요하다. |
| HCI는 항상 CPU와 스토리지를 함께 늘려야 한다 | 일반적으로 노드 확장 중심이지만 제품별 지원 방식이 다르다. |
| HA는 장애가 나도 중단이 전혀 없다 | 일반적인 VM HA는 재시작과 복구 시간이 필요하다. |
| 고장 난 서버에서 라이브 마이그레이션한다 | 원래 호스트가 이동에 참여할 수 있어야 한다. |
| 복제가 있으면 백업이 필요 없다 | 잘못된 변경도 복제될 수 있어 목적이 다르다. |
| HCI와 클라우드는 같은 뜻이다 | HCI는 아키텍처, 클라우드는 서비스 제공 모델이다. |

## 14. 핵심 요약과 복습 문제

### 14.1 한 문장씩 기억하기

- **IDC**: 서버를 안정적으로 운영하는 시설.
- **CPU**: 명령과 연산을 처리하는 장치.
- **RAM**: 실행 중인 프로그램과 데이터가 머무는 작업 공간.
- **하이퍼바이저**: 물리 자원을 관리하면서 VM을 실행하는 계층.
- **VM**: 독립된 운영체제를 실행하는 가상 컴퓨터.
- **vCPU**: VM에 제공하는 가상 프로세서.
- **클러스터**: 여러 노드가 협력하도록 구성한 시스템.
- **SDS**: 저장 서비스와 정책을 소프트웨어로 제어하는 방식.
- **3-Tier**: 컴퓨팅·스토리지 네트워크·외장 스토리지를 분리한 전통적 인프라.
- **CI**: 별도 구성 요소를 사전 검증하고 통합해 제공하는 방식.
- **HCI**: 컴퓨팅과 스토리지를 소프트웨어로 결합하여 통합 운영하는 아키텍처.
- **네트워크 가상화**: 물리망 위에 논리적인 연결과 분리를 제공하는 기술.
- **VM HA**: 장애가 발생하면 다른 호스트에서 VM을 복구하는 기능.
- **라이브 마이그레이션**: 실행 중인 VM을 다른 호스트로 옮기는 기능.
- **클라우드**: 자원을 필요에 따라 요청·사용·반납할 수 있게 제공하는 모델.

### 14.2 복습 문제

1. IDC 안에 HCI와 3-Tier가 동시에 존재할 수 있을까?
2. RAM 128GB 서버 3대를 묶으면 RAM 300GB VM을 바로 실행할 수 있을까?
3. SSD 2TB가 3개이고 전체 사본 2개를 유지한다면 사용자 용량은 얼마일까?
4. 서버 점검 전 VM 이동과 서버 고장 후 VM 복구는 각각 어떤 기능일까?
5. HCI 관리자가 수동으로 VM을 만들어 주는 환경은 그 자체만으로 클라우드일까?

### 14.3 정답

1. **가능하다.** 시설과 인프라 구성 방식은 서로 다른 구분이다.
2. **일반적인 VM에서는 불가능하다.** VM이 실행될 개별 호스트의 메모리 수용 능력이 필요하다.
3. **단순 계산으로 약 3TB다.** 실제 사용 가능 용량은 시스템 사용량과 여유 공간 등으로 더 줄어든다.
4. **점검 전 이동은 라이브 마이그레이션, 장애 후 재시작은 일반적인 VM HA다.**
5. **그 사실만으로는 아니다.** 셀프서비스·자동화·탄력성·사용량 측정 등 서비스 제공 특성을 함께 봐야 한다.
