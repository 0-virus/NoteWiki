## 커버리지란 무엇인가

테스트 커버리지는 "테스트를 실행했을 때 소스 코드 중 실제로 실행된 부분의 비율"이다. 100%라고 해서 버그가 없다는 뜻은 아니다 — 코드가 **실행은 됐지만 결과를 검증(assert)하지 않았을 수도 있기 때문** 이다. 그래도 커버리지가 낮으면 "애초에 테스트가 그 코드를 지나가 본 적조차 없다"는 뜻이라, 최소한의 안전망으로 쓴다.

측정 방식은 여러 가지가 있는데 우리가 기준으로 삼는 두 가지는 **Line Coverage** 와 **Branch Coverage** 다. 이 둘은 다른 것을 측정하고, 하나만 보면 놓치는 부분이 생긴다.

## Line Coverage (라인 커버리지)

**소스 코드 줄(line) 중 테스트 실행 중 한 번이라도 실행된 줄의 비율.** 가장 이해하기 쉬운 지표지만, 그만큼 허점도 크다.

```kotlin
fun getDiscount(user: User): Int {
    if (user.isVip && user.orderCount > 10) {   // 1번 줄
        return 20                                // 2번 줄
    }
    return 0                                     // 3번 줄
}
```

테스트가 `user.isVip = true, orderCount = 11` 인 경우 **하나만** 있어도 1, 2번 줄이 실행되고, VIP가 아닌 경우 테스트가 하나 더 있으면 3번 줄도 실행된다. 이 두 테스트만으로 \*\*Line Coverage는 100%\*\*가 된다.

**하지만 이 코드에는 검증되지 않은 경우가 남아있다**: `isVip = true` 인데 `orderCount = 5` 인 경우(즉 `&&` 의 앞은 참, 뒤는 거짓)는 한 번도 테스트되지 않았다. 1번 줄은 "실행됐다"고 표시되지만, 그 줄 안에 있는 **조건 분기 중 일부는 검증되지 않은 채로** 100%가 나온 것이다.

## Branch Coverage (브랜치 커버리지)

**조건문(`if`, `while`, `&&`, `||`, `when` / `switch` 등)이 만들 수 있는 모든 분기(참/거짓, 각 케이스) 중 실제로 테스트에서 거쳐간 비율.** 위 예제에서 `if (user.isVip && user.orderCount > 10)` 이 가질 수 있는 분기는 다음 4가지 조합이다.

| `isVip` | `orderCount > 10` | 전체 조건 결과 | 테스트했는가 |
| --- | --- | --- | --- |
| true | true | true (할인 적용) | ✅ |
| true | false | false | ❌ **놓친 케이스** |
| false | true | false | ❌ |
| false | false | false (기본 케이스로 커버) | ✅ |

Line Coverage는 100%였지만, Branch Coverage 기준으로 보면 이 조건식의 분기 조합 중 절반만 테스트된 상태다. **이게 Branch Coverage 기준을 Line Coverage보다 낮게(90% vs 80%) 잡는 이유이기도 하다** — 분기 조합 수는 조건이 겹칠수록 기하급수적으로 늘어나서(`&&` / `||` 가 3개면 최대 8가지 조합), 100%에 가깝게 맞추려면 비용이 급격히 커진다. 그래서 실무에서는 "라인은 거의 다 지나가게, 분기는 웬만큼 다양하게"를 목표로 두 지표에 다른 임계치를 둔다.

## 왜 둘 다 봐야 하는가

- **Line Coverage만 보면**: 위 예제처럼 한 줄에 여러 조건이 묶여 있을 때 절반만 테스트하고도 100%로 착각한다.
- **Branch Coverage만 보면**: 분기가 거의 없는 단순 유틸 함수(포맷터 등)는 Branch Coverage가 애초에 의미가 적다 — 이런 코드는 Line Coverage로 충분하다.
- 그래서 두 지표를 **함께** 기준으로 삼고, 조건 분기가 많은 핵심 로직(인증/권한/감사)은 둘 다 100%를 요구한다.

## 백엔드 커버리지 (JaCoCo)

| 구분 | Line | Branch |
| --- | --- | --- |
| 일반 Service / Controller | 90%+ | 80%+ |
| 핵심 비즈니스 (인증/권한/감사) | 100% | 100% |

핵심 분류 기준:

- `*.core.security.*` (JWT, SecurityFilterChain)
- `*.domain.auth.*`
- `*.domain.common.audit.*`

이 세 패키지는 조건 분기 하나만 놓쳐도 "인증 우회" 같은 심각한 결함으로 이어질 수 있어 100%를 요구한다. 반대로 일반 Service는 모든 분기를 다 테스트하는 비용이 이득보다 커지는 지점이 있어 80%로 현실적인 선을 둔다.

```bash
./gradlew test jacocoTestReport
./gradlew jacocoTestCoverageVerification   # 임계치 미달 시 빌드 실패
```

리포트 위치: `build/reports/jacoco/test/html/index.html` — HTML 리포트를 열면 **줄 옆에 초록/빨강/노랑** 으로 표시된다. 노랑이 바로 "이 줄은 실행됐지만 분기 중 일부만 테스트됨"이다 (위 예제 상황).

## 프론트 커버리지 (Vitest + v8)

Vitest의 v8 coverage provider로 측정하며, lcov 리포트를 SonarQube에 연동한다. 개념(Line/Branch)은 백엔드와 동일하고, 여기에 **Function Coverage** (함수 자체가 한 번이라도 호출됐는가)와 **Statement Coverage** (세미콜론으로 끝나는 개별 구문 단위, Line보다 더 세밀함)가 추가로 리포트에 나온다.

```bash
pnpm test:coverage
```

리포트 위치: `coverage/index.html`, `coverage/lcov.info`

## 체크리스트

- 리포트에서 노란색(분기 일부 누락) 줄이 있는지 확인했는가 — Line 100%라고 안심하지 않았는가
- 인증/권한/감사 관련 코드가 100% 기준을 충족하는가
- 조건이 3개 이상 겹친 복잡한 `if` 는 분기를 쪼개서 테스트 가능하게 리팩터링을 검토했는가
